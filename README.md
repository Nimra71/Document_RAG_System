# Document RAG System — Production Version

An intelligent document Q&A API: upload a PDF, ask natural-language questions, get
grounded answers with source citations. Rebuilt from the original Gradio prototype
into a containerized, cloud-deployed FastAPI service.

## What's new vs. the original version

- **FastAPI backend** instead of Gradio — proper REST API, usable by any frontend
- **Two-stage retrieval**: FAISS retrieves candidates, a cross-encoder re-ranks them
  for higher-precision context selection
- **Conversation memory** — session-based chat history for natural follow-up questions
- **Source citations** — every answer includes which chunk(s) it was grounded in
- **Groq API** for generation instead of a local GPU model — runs entirely on
  CPU-only infrastructure, so it deploys for free
- **Dockerized** and **CI/CD via GitHub Actions** — pushes to `main` auto-deploy to
  Google Cloud Run

## Local setup

1. Install dependencies:
   ```
   pip install -r requirements.txt
   ```

2. Get a free Groq API key at https://console.groq.com/keys

3. Set it as an environment variable:
   ```
   export GROQ_API_KEY=your_key_here
   ```

4. Run the server:
   ```
   uvicorn app.main:app --reload
   ```

5. Open http://localhost:8000/docs — FastAPI auto-generates an interactive UI
   where you can test every endpoint (upload a PDF, ask questions, etc.) without
   writing any client code.

## API endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/health` | Health check |
| POST | `/upload/{session_id}` | Upload a PDF for a given session |
| POST | `/ask/{session_id}` | Ask a question about the uploaded document |
| POST | `/summarize/{session_id}` | Get a summary of the document |
| GET | `/history/{session_id}` | View conversation history |

`session_id` can be any string you choose (e.g. a UUID generated by your frontend)
— it lets multiple users/documents be handled independently.

## Running with Docker

```
docker build -t document-rag-system .
docker run -p 8080:8080 -e GROQ_API_KEY=your_key_here document-rag-system
```

## Known limitations / good interview talking points

- Session data is stored in-memory — it resets on server restart and won't be
  shared across multiple instances if Cloud Run scales up. A production version
  would use Redis for shared session state.
- Chunking is a simple fixed-size sliding window; a more advanced version could
  chunk by semantic/paragraph boundaries.
